[28] ABSTRACT
[29] Smart Expenses Tracker is a native Android application designed to help users record, organize, and review personal income and expenses. Traditional paper-based tracking requires manual calculations and can be lost, while some cloud-dependent applications are less useful when internet access is unavailable. This project addresses these concerns through a local-first design in which transactions are stored in a Room SQLite database on the device before cloud synchronization is attempted.
[30] The Android client is developed using Java and XML and follows an MVVM-style structure with Data Access Objects (DAO). Monetary values are stored as integer minor units—paise for Indian rupees—to avoid floating-point arithmetic errors during storage and calculations. The application also includes transaction categories, multiple account types, a bilingual Hindi-English voice-entry workflow, and background synchronization using Android WorkManager. A Node.js/Express REST API connects the client to a Supabase PostgreSQL database protected by Row Level Security. A React/Vite administrative panel provides service-health and system telemetry functions while the design aims to protect users’ plaintext financial records.
[31] The intended outcome is a responsive expense-tracking application that remains usable offline and synchronizes pending records when connectivity returns. The project provides practical experience in native Android development, local database design, API integration, cloud persistence, interface design, and software testing.
[32] The project focuses on a common personal-finance problem: users need a convenient way to record income and expenses while retaining access to their records when a network connection is unavailable. A finance application should not make a basic task such as recording a cash purchase dependent on a successful internet request. It should also preserve monetary values accurately, organize records for later review, and provide a clear path for recovering information when the device reconnects. SMART EXPENSES TRACKER is designed around these requirements through a local-first approach in which a transaction is written to the device before cloud synchronization is attempted.
[33] The Android client uses Java and XML layouts, with Room SQLite for local persistence and DAO interfaces for structured database operations. Monetary values are represented as integer minor units (paise) rather than binary floating-point values. The system design also includes background synchronization through WorkManager, a Node.js/Express REST API, Supabase PostgreSQL storage with Row Level Security, and a React/Vite web administration panel for service-health and account-level observability. A bilingual voice-entry flow is included to make transaction recording more accessible to users who prefer speaking in Hindi or English. Voice input is intended to be confirmed or cancelled before the transaction is saved.

[46] Personal expense tracking helps students, working professionals, and small business owners understand their spending and manage budgets. Paper diaries and spreadsheets require manual entry and calculations, while cloud-reliant applications may be inconvenient without internet access. Storing currency in floating-point types can also introduce rounding inaccuracies. Smart Expenses Tracker is designed to address these issues through local-first transaction storage, integer-based monetary values, and cloud backup and synchronization.

A user may make several small purchases throughout a day, receive income from different sources, or move money between cash, bank accounts, and digital wallets. The application is intended to provide one place for recording transactions and organizing them into categories and accounts.
[48] The design addresses three concerns identified in the source report: network dependency, arithmetic accuracy, and data recovery. Local storage allows a transaction to be recorded without waiting for a server response. Integer paise values avoid the common rounding behaviour associated with binary floating-point arithmetic. Cloud synchronization provides a route for restoring or accessing records beyond a single local database, subject to successful configuration and operation of the backend. These choices are intended to improve reliability without making the user manage technical details manually.

[71] 3. SYSTEM ANALYSIS
[72] 3.1 Existing System and Limitations
[73] Before the proposed application, users commonly relied on handwritten diaries, spreadsheets, or cloud-based expense applications.
[74] Paper diaries and spreadsheets remain simple ways to record spending, but they require manual entry and calculation. A paper record can be misplaced or damaged, and a spreadsheet may become inconsistent if formulas are edited or data is entered in different formats. These methods also require the user to create their own categories, summaries, and backup process. They can work for small personal needs, but they offer limited automation and little support for mobile-first workflows.
[75] Cloud-dependent mobile applications provide convenience and synchronization, but an application that requires a successful server request before saving a transaction may be difficult to use in areas with poor connectivity. Financial calculations can also become unreliable if amounts are represented using floating-point values without suitable handling. Finally, a local-only design without a backup path can leave users vulnerable to data loss after an uninstall or device change. These limitations motivate a design that combines immediate local persistence with later synchronization.
[76] 3.2 Proposed System and Advantages
[77] The proposed system uses a local-first data flow. When the user enters a transaction, the Android client validates the input and saves it to Room SQLite. The interface can then display the new record without waiting for a remote server. A synchronization worker checks for pending changes and sends them to the backend when network access is available. This arrangement separates the user's immediate task from the availability of remote infrastructure and makes the application more tolerant of temporary network interruptions.
[78] The proposed system also applies integer minor-unit storage for currency, structured categories and accounts, and a bilingual voice-entry option. Cloud persistence provides a second storage location, while the administration panel supports operational checks. The design aims to balance usability and technical reliability: a simple transaction workflow is backed by explicit storage, synchronization, and access-control responsibilities. The stated advantages depend on correct implementation, backend configuration, and testing on the target devices.

[91] 4. SYSTEM DESIGN
[92] 4.1 System Architecture
[93] The system is organized into three logical tiers:
[94] • Android client: Activities and Fragments form the interface; ViewModel/LiveData manage UI state; Room SQLite stores transactions locally; the voice engine handles bilingual voice input; WorkManager schedules background synchronization.
[95] • REST API tier: The Node.js/Express backend receives authenticated requests over HTTPS and provides synchronization endpoints.
[96] • Cloud and administration tier: Supabase PostgreSQL stores synchronized data with Row Level Security. A React/Vite web control panel monitors service health and system telemetry.
[97] User Interface → ViewModel / Repository → Room SQLite
[98] Room SQLite ↔ WorkManager SyncManager ↔ HTTPS REST API ↔ Supabase PostgreSQL
[99] React/Vite Admin Panel → API and service-health diagnostics
[100] Figure 4.1: Text representation of the three-tier architecture.
[101] The architecture is organized into three broad tiers. The first tier is the Android client, which contains Activities or Fragments, presentation logic, the Room database, the voice-entry workflow, and WorkManager-based background processing. The second tier is the REST API gateway implemented with Node.js and Express. It receives requests from the client, applies server-side checks, and coordinates database operations. The third tier contains Supabase PostgreSQL and the React/Vite administration panel. The database is the remote persistence layer, while the panel is intended for technical monitoring and account-level administration.
[102] The local database is the primary immediate destination for a new transaction. When connectivity is available, the synchronization component sends pending records to the API over HTTPS. The server then writes or updates the corresponding cloud records. A successful response allows the client to update its synchronization status. A pull operation can retrieve cloud-side changes and update local records. The boundaries between tiers are important because the mobile interface should not directly bypass the API's validation or security controls.

[109] 4.3 Activity Flow: Transaction and Voice Lifecycle
[110] 1. The user starts a transaction and chooses keyboard entry or microphone input.
[111] 2. For voice input, the voice engine parses the amount, category, and intent. The user may confirm with a phrase such as “save kardo” or cancel with “mat karo”.
[112] 3. The amount is converted to integer paise; for example, ₹500.00 becomes 50,000 paise.
[113] 4. The transaction is stored in Room SQLite and the local interface is updated.
[114] 5. If the device is offline, the transaction remains marked as unsynchronized and the background task can retry later.
[115] 6. When internet access is available, the synchronization engine sends pending records to the REST API.
[116] 7. The backend writes or updates records in Supabase PostgreSQL. After a successful response, the local record is marked as synchronized.
[117] Figure 4.3: Activity flow for manual and voice transaction entry.
[118] The transaction lifecycle begins when the user chooses manual entry or voice input. In manual entry, the user supplies an amount and selects the relevant transaction details. In voice entry, the voice engine attempts to identify the amount, category, and intended action from the spoken phrase. The parsed result should be shown or confirmed so that an incorrect recognition does not silently become a financial record. A confirmation phrase such as “save kardo” can proceed with the operation, while “mat karo” cancels it.
[119] After validation, the amount is converted into integer paise and the transaction is written to the local database. The interface can update from the local record. If the device is offline, the record remains pending and the synchronization worker can retry later. If the device is online, the worker sends the record to the API, which persists it in the cloud database. The client updates the local synchronization flag only after a successful server response. Each transition should have a clear success or failure state so that users can understand whether a transaction was saved locally and whether it has synchronized.
[120] 4.4 Class Model: Local Database Entities
[121] The local data layer includes AppDatabase, TransactionDao, AccountDao, CategoryDao, TransactionEntity, AccountEntity, CategoryEntity, and SyncManager.
[123] The class model shows how the local database and supporting modules cooperate. AppDatabase provides access to the database instance and exposes the required DAO interfaces. TransactionDao is responsible for transaction queries and updates, while account and category DAOs support related information. TransactionEntity represents an individual transaction and contains fields needed to identify, categorize, store, and synchronize it. SyncManager coordinates the upload and download operations without placing network logic directly inside the user interface.
[124] Keeping database access behind DAO interfaces makes the application easier to maintain. UI components can request or observe data through the appropriate application layer instead of constructing SQL queries themselves. Entity fields should have consistent types and constraints, and database migrations should be considered if the schema changes in later versions. The class model is therefore both a structural description and a guide for keeping responsibilities separate.
[125] 4.5 Sequence Flow: Two-Way Synchronization
[126] 1. The UI creates a transaction and stores it locally with isSynced = false.
[127] 2. The local interface reflects the new transaction without waiting for a network response.
[128] 3. The synchronization manager queries the local database for unsynchronized transactions.
[129] 4. Pending records are sent to the Express API using an authenticated JSON request.
[130] 5. The backend upserts records into the Supabase transactions table.
[131] 6. After a successful response, the local database marks the submitted records as synchronized.
[132] 7. The client requests cloud changes through the pull endpoint and inserts or updates the corresponding local records.
[133] Figure 4.5: Sequence summary for two-way synchronization.
[134] The synchronization sequence begins when a transaction is created locally with its synchronization flag set to false. The local interface displays the transaction immediately, while the synchronization manager later queries for pending records. Those records are sent to the Express API using a structured request. The backend validates the request and inserts or updates the corresponding records in Supabase PostgreSQL. Once the server confirms success, the client marks the submitted local records as synchronized.
[135] The pull phase handles changes that exist remotely but are not yet reflected on the device. The client requests the relevant cloud records, then inserts or updates the local database. A robust implementation must account for retries, repeated requests, partial failures, and duplicate submissions. Idempotent record identifiers help prevent a retry from creating a second copy of the same transaction. The synchronization status should be updated only when the corresponding operation has actually succeeded; otherwise, the item should remain eligible for a later retry.

[155] The application follows the Model-View-ViewModel (MVVM) pattern with Data Access Object (DAO) abstraction. Activities and Fragments provide the view layer; ViewModel and LiveData manage UI state; repositories and SyncManager coordinate data operations; and Room SQLite and the Express API provide local and remote data access.
[156] View (Activities / Fragments) ↕ ViewModel / LiveData ↕ Repository / SyncManager ↕ Room SQLite ↔ Express API / Supabase
[157] An incremental development methodology is suitable for this project because the application contains multiple dependent components. Each iteration can deliver and test a small part of the workflow before additional features are introduced. A useful sequence is requirement identification, interface and data-model design, local transaction implementation, synchronization integration, voice workflow integration, administrative panel development, and final testing. At each stage, errors should be recorded and corrected before the next stage adds further complexity.
[158] The architecture follows an MVVM-style separation with DAO-based persistence. Presentation components are responsible for displaying information and receiving user actions; application logic coordinates validation and transaction operations; DAOs provide database access; and repositories or synchronization managers coordinate local and remote data. This structure reduces direct dependencies between screens and data operations and makes the code easier to review.
[159] 6.2 Key Architectural Modules
[160] 1. Financial Minor-Units Engine
[161] Monetary amounts are stored as integer paise instead of floating-point values. The conversion is: Amount in paise = Amount in INR × 100. For example, ₹50,000.00 is stored as 5,000,000 paise. Conversion to a formatted rupee amount is performed at the display boundary.
[162] 2. Local-First Room DAO Module
[163] Room provides type-safe access to the local SQLite database. Transaction records are saved locally before synchronization, allowing the application to display updated information when the device is offline.
[164] 3. Background Synchronization Engine
[165] SyncManager queries records whose isSynced flag is false, packages them into JSON, and sends them to the push endpoint. After a successful response, the records are marked as synchronized. The pull process retrieves cloud records to restore local data when required.
[166] 4. Bilingual Voice Assistant and Smart Back Navigation
[167] The voice workflow parses Hindi and English phrases into structured transaction details. Confirmation phrases such as “kardo” and cancellation phrases such as “mat karo” determine whether the transaction proceeds. Smart back navigation returns the user to the Home tab from other tabs; pressing back twice from Home is used as an exit safeguard.
[168] The major modules are designed to operate together while maintaining clear responsibilities. The financial minor-units engine validates amounts and converts rupees into paise. The local database module stores transaction records and provides queries through DAO interfaces. The synchronization engine identifies pending records and coordinates push and pull requests. The voice assistant interprets spoken input and requires a confirmation or cancellation decision. Navigation safeguards reduce accidental exits and help users move through the application predictably.
[169] Each module should expose a small set of methods and communicate through defined data structures. Error handling should cover invalid amounts, missing required fields, unavailable microphone permissions, unsuccessful network requests, and database failures. Separating these concerns makes the application more maintainable and allows individual modules to be tested without repeating the entire end-to-end workflow.

[174] 6.4 DAO and Synchronization
[175] The TransactionDao provides operations for inserting transactions, retrieving a user’s transactions in descending date order, selecting unsynchronized records, and marking records as synchronized. SyncManager uses these DAO operations to coordinate background push synchronization. Failed requests remain eligible for retry.
[176] A Data Access Object (DAO) provides a controlled interface for database operations. It can include methods to insert a transaction, update a record, retrieve recent activity, filter records by category or account, and find all unsynchronized transactions. Keeping these methods in the DAO layer prevents database queries from being duplicated across multiple screens and gives the application one consistent way to read and modify local data.
[177] The synchronization manager uses DAO methods to find pending records, sends them through the REST API, and updates their synchronization status after confirmed success. Network failures should not delete local records or mark them as synchronized. WorkManager can schedule a retry when the required network constraint is satisfied. The push and pull operations should also be safe to repeat, because mobile connectivity may fail between sending a request and receiving its response.
[178] 6.5 Main Application Modules
[179] Implementation translates the design into working modules and connects them through defined interfaces. The application should be developed incrementally: first establish the Android project and navigation, then create the database entities and DAOs, implement transaction entry, and connect the presentation layer to local data. Background synchronization and the remote services can be integrated after local persistence is stable. This sequence reduces the number of variables involved when debugging an error and helps isolate whether a problem originates in the interface, database, network request, or backend.
[180] The implementation approach emphasizes separation of concerns. Java classes handle application logic, XML defines the interface layouts, Room manages local data access, and WorkManager schedules synchronization work. The backend validates incoming requests and coordinates cloud persistence. The web panel is maintained separately from the Android client. These boundaries support clearer testing and make later changes less likely to affect unrelated modules.
[181] The main mobile modules include authentication or account access, the dashboard, transaction entry, account management, category selection, transaction history, insights, voice input, local persistence, and synchronization. The dashboard provides an overview of the user's financial activity, while transaction history supports review of individual records. Account and category management organize transactions so that later summaries are more useful than a single unstructured list.
[182] The backend and administration modules complement the mobile application. The API accepts requests from the client, validates their structure, and communicates with the cloud database. The administration panel provides a controlled view of service health and account-level status. Module integration should be checked with both successful and unsuccessful cases, including invalid inputs, unavailable connectivity, expired or missing authentication, and backend errors.

The modular structure is intended to make the application easier to maintain and extend.
